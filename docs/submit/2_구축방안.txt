■ 구성: LLM은 해석과 문장, 코드는 숫자와 판단, 사람은 승인
- OpenAI Agents SDK 0.24.0 + Responses API(Structured Outputs)로 만듭니다. Agent Builder(11-30 종료)와 호스티드 Evals(10-31부터 읽기 전용)는 쓰지 않고 평가는 자체 하네스로 합니다.
- 에이전트 도구: 회차 숫자표 조회, 문항 은행 변경안(폐기·승격·새 문항과 근거), 다음 설문 초안, 설문 발송, 액션플랜 배포. 설문 발송과 플랜 배포는 needs_approval로 담당자 승인 없이는 실행되지 않습니다.
- 출력 가드레일: 플랜 문장은 숫자마다 인용 키를 달아야 하고, 검증기가 표에서 다시 계산해 하나라도 틀리면 배포를 막습니다.

- 흐름: 누적 자료→문항 은행→설문 구성→(승인)→발송·취합→분류→분석·배정→액션플랜(검증)→(승인)→실행→ERP 매출→진화→다음 설문. 분기 1회.
- 담당자 화면: 추천 액션과 대상 거래처, 근거 문항과 효과 크기, 다음 설문에서 바뀌는 문항과 이유. 영업은 거래처별 방문 리스트, 마케팅은 캠페인 타깃 리스트를 받습니다.

■ 모델 배분(오류가 다음 단계로 번지는지, 되돌릴 수 있는지로 정함)
- 개방형 응답 1차 분류(대량·되돌릴 수 있음): gpt-6-luna(Decisions API를 쓸 수 있으면 선택형 분류로). 사람이 분류한 200건과 일치도(κ)를 재서, 선행연구의 zero-shot 수준(GPT-4o, 독일어 설문 5,072건에서 κ 0.76)에 못 미치면 판정 모델로 올립니다.
- 코딩 불일치 판정·새 문항 문구·플랜 문장(고객에게 나가거나 경영 판단에 쓰임): gpt-6.1-sol.
- 누적 자료 중 스캔본·표 이미지: gpt-6.1-terra.
- 결정 기여도·효과 추정·배정·폐기/승격: 결정론 코드(LLM 미사용). 합성 응답자는 응답을 동질화한다는 연구 결과가 있어 의사결정에 쓰지 않습니다.

■ 데이터 파이프라인
- 입력 어댑터 3종: 누적 설문(hwp·pdf·xlsx·csv)→문항 은행, 응답(폼·엑셀)→표준 응답표, ERP 분기 매출→결과표. 형식이 바뀌면 어댑터만 고칩니다.
- 고객 식별자 가명 처리와 개인정보 LLM 비전송은 본선 어댑터에서 구현합니다(현재 프로토타입은 가명 ID만 다루는 시뮬레이션).

■ 통계 설계
- 회귀식: 매출 변화율 = 액션 주효과 + 문항 + 액션×문항 상호작용(릿지). 문항의 결정 기여도 = 상호작용 계수의 최대 |t|.
- 추첨 대조군 15%(불변 하한 10%). 배정이 관측된 응답에만 의존하므로 응답을 통제한 회귀에서 효과로 읽힙니다. B2B는 거래조건(리베이트·단가)을 추첨하지 않고 서비스성 액션만 추첨하며, 첫 분기는 기존 배정을 유지하고 15%만 추첨합니다(이 제약을 건 시뮬레이션에서도 Q-Loop 우위 +2.7%p).
- 진화 규칙: 기여도 |t|<1.0이 2회 연속이면 폐기, 새 문항은 |t|≥2.0이 2회 연속이면 승격, 회차당 폐기·추가 각 2개, 응답 상관 0.7 이상 중복 정리, 폐기 4분기 뒤 재시험, 대조군 기준 이득이 2표준오차 넘게 떨어지면 직전 변경을 되돌림.
- 불변 영역(진화기가 못 건드림): 추세용 앵커 문항, 대조군 하한, 검증기, 가명 처리.
- 알려진 약점과 보완: ①고객이 적은 B2B는 폐기 판단의 28~30%가 실제 신호 문항이었음 → 3분기치를 묶어 세그먼트 간 정보를 빌리는 계층 모델로 추정하고, B2B 문항 폐기는 담당자 승인을 거침 ②액션 여러 개 중 최대 |t|라 우연히 큰 값이 나올 수 있음 → 근거 표시는 |t|≥3만(시뮬레이션에서 82건 중 80건 정확), 폐기·승격 임계값은 순열 귀무분포로 보정.

■ 검증 현황(저장소 lotte-ax-qloop, 실측)
- 실제 OpenAI 모델 출력(VPS의 Codex CLI, 기본 모델 gpt-5.6-sol, 11-03): 숫자표만 주고 플랜 문장을 쓰게 한 3회 69문장 중 숫자를 지어낸 문장은 0개였습니다. 오히려 검증기 v1이 첫 회 24문장 중 맞는 문장 9개를 막았습니다(t값을 근거로 '근거 문항 없음'이라 쓴 8개, 숫자 없는 순위 주장 1개). 문장 유형별(값·근거 없음·순위)로 판정하게 고친 v2는 그 24개를 모두 통과시켰고, v2가 보지 않은 2회 45문장에서는 39개 통과·6개 차단이었습니다(6개 모두 맞는 문장, 과잉 차단). 본선에서는 막힌 문장을 버리지 않고 담당자 확인으로 넘깁니다. 개방형 응답 87건 분류 정답은 모델 82~84건(3회), 사전 코더 75건입니다.
- 공격 시험: 틀리게 바꾼 문장 1,323/1,323 차단(근거가 있는데 없다고 쓰기·틀린 순위 포함), 맞는 문장 420/420 통과. 검증기가 못 잡는 것은 숫자에 붙인 이름(모델이 t값을 '효과 지표'라 부름)이라 사람 검토로 남깁니다.
- 에이전트 코드가 시뮬레이션 정답 모듈을 import하지 못하게 시험으로 막았고, Agents SDK 배선은 키 없이 구성·가드레일 차단까지 확인했습니다.

■ 본선 1박 2일 계획(현장 데이터·구체화된 과제 당일 공개 전제)
- 0~2시간: 데이터 구조 파악, 어댑터 3종 매핑. 매출이 없으면 재구매·문의 같은 대리 결과로 바꿉니다.
- 2~6시간: 누적 자료를 문항 은행으로 적재, 첫 회차 분석.
- 6~12시간: 액션플랜·검증기·승인 흐름 연결.
- 12~18시간: 현장 과거 회차를 순서대로 다시 돌리는 백테스트로 진화 규칙의 효과를 현장 데이터에서 측정.
- 18~24시간: 담당자 화면과 발표. 측정한 숫자만 씁니다.
- 사전 작성 코드 사용 가능 여부는 미확인입니다. 허용되면 저장소를 그대로 쓰고, 불허면 설계·규칙·시험 케이스만 가져가 핵심부(분석·진화·검증 약 560줄)를 다시 구현합니다.

■ 성과 지표
설문 문항 수, 응답률, 대조군 대비 액션 순이익, 개방형 코딩 κ, 검증기 차단율, 되돌리기 횟수.
